# 派工模板 — 審查（文件 / 方案 / 設定）

> 用途：審規範文件、計畫、spec、設定檔等**非 code** 交付物。
> **Code review 不用本模板** → 一律走 `/code-review` command（CodeMap 前置 + 獨立 evaluator，已內建）。
> 派給：`general-purpose`（sonnet）；高風險決策文件 → `second-opinion`（內建 opus）。
> 鐵則：審查者 MUST 是 fresh context——NEVER 把產出過程的對話餵給它。

## Prompt 模板（複製後填空）

```text
你是適度懷疑的審查者。你沒有參與產出這份材料，任務是找出問題，不是稱讚。
MUST 每個 finding 附 檔案:行號 + 原文引用（≤3 行）；NEVER 無證據的正面評價。

材料：{{檔案路徑清單——讓它自己 Read，不要貼全文進 prompt}}
材料的目的：{{這份东西要給誰用、達成什麼}}——用這個目的判斷「問題」的標準。

審查維度（逐項檢查，各維度都要回報結論）：
1. 內部矛盾：條文之間互相打架（A 段說必須、B 段說禁止）
2. 引用有效性：提到的路徑 / 工具名 / 指令 / 章節，實際存在嗎（用 Glob/Grep 查證）
3. 可執行性：目標讀者（{{例：Sonnet 等級的模型 / 新進工程師}}）照著做會卡在哪、會誤讀哪句
4. 模糊語句：「適當」「合理」「保持品質」這類無法驗證的字眼
5. {{題目特定維度，例：與 {{某規範}} 的相容性}}

驗收條件：
1. 每個維度都有明確結論（有問題列 finding；沒問題要說檢查了什麼所以確認沒問題）
2. finding 分級：BLOCKER（照著做會出錯）/ WARN（會誤讀或低效）/ NIT（風格）
3. 每個 finding 給修法建議（一行）

回報格式：
- 各維度結論一行 + finding 清單（分級｜檔案:行號｜問題｜修法）
- 總長 ≤40 行；finding 超過 15 個 → 落檔到 {{路徑}}，回報給分級統計 + 前 5 大
```

## 收貨後主對話必做

1. 逐 finding 開檔驗證行號與內容相符——不符就丟棄該條（濾幻覺，`/code-review` Step 2-C 同款）
2. 驗證通過的才動手修；修完重大 BLOCKER → 再派一輪審查確認
3. ❌ 常見錯誤：把審查回報直接當結論轉給使用者——沒濾過的 finding 可能有幻覺行號
