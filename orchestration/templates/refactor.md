# 派工模板 — 重構

> 用途：行為不變的結構調整（抽 function、換 pattern、搬檔案、去重複）。
> 派給：`general-purpose`（sonnet）；若是「已定案 pattern 套用到多檔」→ 改派 `batch-worker`（附 before/after 範例）。
> 重構的靈魂是「行為不變」——驗收圍繞這一點設計。

## Prompt 模板（複製後填空）

```text
目標：把 {{重構對象}} 從 {{現狀}} 改成 {{目標結構}}。
動機：{{為什麼值得動：重複 N 處 / 每次改都要動 M 個檔 / 擋住了接下來的 X}}。

行為不變基準（動手前先建立，這是驗收的錨）：
1. 先跑 {{test / build 指令}}，記錄通過清單——這是 baseline
2. 若沒有測試覆蓋：先對 {{關鍵入口}} 記錄「輸入 → 輸出」樣本 {{N}} 組（實跑取得，不是用想的）

範圍鐵則：
- 只動 {{檔案 / 目錄清單}}
- NEVER 改 public API 簽名 / 對外行為 / 設定格式——除非本次目標就是改它（是的話列在這：{{清單}}）
- NEVER 順手修 bug 或加功能——發現 bug 記進「額外發現」，行為照舊保留（連 bug 都要不變）

驗收條件（verifier 會逐條打分）：
1. baseline 的測試 / 輸入輸出樣本，重構後結果完全一致
2. {{結構目標，例：X 邏輯只剩一份，位於 {{目標位置}}；原 N 處呼叫點全部改指向它}}
3. 無殘留：舊實作已刪除，無 dead code / 未使用 import（用 {{lint 指令}} 驗）
4. diff 中不含與目標無關的改動（格式化噪音、無關重排）

回報格式：
- baseline 建立方式與結果（≤3 行）
- 改動清單：檔案:行號範圍｜做了什麼
- 驗收逐條自報 + 證據；額外發現（含刻意保留的 bug）
- 總長 ≤30 行
```

## 填空要點

- 沒有 baseline 就開始重構 = 沒有安全網；subagent 回報裡沒有 baseline 段 → 直接退件
- 「連 bug 都要不變」不是玩笑：行為改變（哪怕變對）會讓 diff 無法用「一致性」驗收
- ❌ 常見錯誤：目標寫「讓 code 更乾淨」——驗收不了；要寫成結構事實（「X 只剩一份」「Y 不再依賴 Z」）
