# Judgment — 判斷力外化 rubric

<system_context>
把「需要判斷力」的決定寫成可執行的判準，給任何等級的模型照著走。
每條 rubric 附正例與反例——對照時找「與我現況同構的例子」，不要憑感覺。
機械性的升降級規則（FAIL 次數計算）在 `dispatch.md §升降級路徑`；本檔管「還沒 FAIL 但該預判」的部分。
</system_context>

## 1. 何時該升級模型（在失敗發生之前）

滿足任一條 → 這個子任務直接派 `opus`（不要先讓 sonnet 試錯一輪浪費時間）：

- **約束互相牽制**：改動要同時滿足 3 個以上會互相衝突的條件（改 A 會破 B）
- **一次性高後果**：結果會被長期沿用且事後難改（架構選型、公開 API 形狀、規範文件的結構）
- **除錯已死兩個假設**：你提出的前兩個原因假設都被證據推翻了
- **品味成分高**：好壞差異說不成可驗證條件（文案語氣、架構優雅度）——升級之外還要走 §6

✅ 正例：「重排框架檔案結構，要同時滿足 doctor 對帳通過、單檔 ≤200 行、弱模型讀得懂」——三約束互相牽制 → 直接 opus。
❌ 反例：「把 20 個檔案的 `using Foo` 改成 `using Bar`」——量大但機械 → 不升級，這是 `batch-worker`（haiku）的活。量大 ≠ 難。

## 2. 何時算真的完成（Definition of Done)

完成 = 下列全部成立，缺一就還沒完成：

1. 原始要求逐條對照過（要求有 5 點就對 5 點，不是「大方向有做到」）
2. 交付物實際落檔，且經 `verifier` read-back（或至少主對話重新開檔確認，並標明未派驗）
3. 程式碼：build 過 + 測試過 + **實跑過受影響的流程**（`/verify`）——三者是遞進，不是三選一
4. 交付物內無 TODO / TBD / placeholder / 空 section
5. 回報文字裡沒有「應該可以」「大概」「理論上」——出現任一個，代表有事沒驗，回去驗

✅ 正例：改 API → `dotnet build` 過 → 既有測試過 → curl 實打端點回 200 且 payload 正確 → verifier 對驗收條件全 PASS → 完成。
❌ 反例：「已修改 3 個檔案，邏輯上應該能解決問題」→ 第 3、5 條全踩——這是「寫完」，不是「完成」。

## 3. 何時該停下來問使用者

**硬觸發（先問，不動手）**：
- 刪除 / 覆蓋不是你本次建立的內容（含「重寫」既有檔——先備份再問或至少先備份）
- 對外發布：git push、公開 artifact、寄信、打外部 API 寫入
- 花錢、production 變更、動 secrets
- 發現使用者陳述的前提與現實矛盾（他說檔案在 A，實際在 B 且內容不同）——先報告矛盾，不要猜他要哪個
- 任務有兩個合法解讀，且兩者工作量或影響面差 3 倍以上

**不問（自己決定，回報時交代一句）**：
- 可逆、範圍內、repo 已有慣例可循的選擇
- 問題用一至兩輪查證（Read / Grep / 官方文件）就能自己回答

✅ 正例：要覆蓋的 config 檔內容跟使用者描述的不一樣 → 停，報告差異，附「保留 / 覆蓋 / 合併」三選項與各自後果。
❌ 反例：「測試框架選 xUnit 還是 NUnit？」repo 裡已全是 xUnit → 不問，跟現狀走，回報提一句。

**問的格式**：附推薦選項 + 每個選項的後果。NEVER 丟開放題（「你想怎樣？」）。

## 4. 換路訊號（方向錯了——重試只會燒 token）

出現任一訊號 → 停止當前做法，回上一個分岔點換方法，並把死路記下來（見 `maintenance.md`）：

- 同一子任務重試 2 輪仍 FAIL（`dispatch.md` 上限）
- **蹺蹺板**：修 A 壞 B、修 B 又壞 A，出現第 2 次——代表抽象層選錯，不是手不穩
- **假進度**：連續兩輪都「快好了」，但驗收條件的 PASS 數沒有增加
- **特例增生**：每過一條驗收就要多加一個 if / 特判，第 3 個特例出現時停
- **hack 疊 hack**：這次的修法是在繞上次修法產生的問題

「換路」= 換方法 / 換工具 / 重切子任務邊界，不是換個措辭重派同一個 prompt。

✅ 正例：手寫正則 parse 設定檔，補了 3 個 edge case 還在漏 → 換現成 parser / AST，不是寫第 4 個補丁。
❌ 反例：測試 FAIL 原因是環境缺依賴 → 這不是方向錯，是環境問題；裝依賴重跑，不算入重試輪數。
（區分法：失敗原因指向「做法本身」→ 換路；指向「環境 / 輸入 / 筆誤」→ 修掉重跑。）

## 5. 品質底線怎麼驗（最低標，不是目標）

| 交付物 | 底線驗法 |
|---|---|
| 文件 / 規範 | `verifier`：內部引用的路徑・工具名・指令實際存在；條文無互相矛盾；無 vague 字（「適當」「合理」「保持品質」）|
| 程式碼 | §2 第 3 條的遞進三驗；非 trivial diff 加 `/code-review` |
| 設定檔（yaml/json） | schema 驗證或 dry-run（k8s yaml → `/k8s-review`）|
| 圖 / 投影片 | 對應 skill 的 checklist（mermaid-diagrams / slide-builder）|

底線以上的「更好」屬品味問題 → §6。

## 6. 誠實條款：這套制度補不了的東西

拆解、驗證、多樣本評審**補得了**：執行品質、疏漏、幻覺、自驗樂觀。
**補不了**：模糊題的問題定義（問題本身不清楚時，流程再嚴謹也是精準地做錯事）、品味判斷（優雅、語氣、取捨輕重）。

遇到補不了的，依序做：
1. 升 `opus` + 派 `second-opinion` 拿獨立第二意見
2. 還是拿不準 → 產 2–3 個候選方案給使用者選，每案附一行後果（把品味判斷還給人）
3. 使用者也說不清 → 明說「這題在我可靠判斷範圍之外，建議 ___」——說做不到比假裝自信有價值

- NEVER 在品味問題上用單一模型單一輸出定案還宣稱「這是最佳方案」
- NEVER 把「流程都跑完了」當成「答案是對的」——流程管執行，不管方向
